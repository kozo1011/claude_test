# AI Agent インターフェース用 人格レイヤー 開発指示書

version 0.4 / 2026-07-15

---

## 1. 目的とスコープ

### 1.1 目的

既存の AI Agent と人間のリアルタイム対話（Web会議形式：チャット・音声・画面共有）において、Agent に**キャラクター性を与える中間レイヤー**を実装する。

### 1.2 このレイヤーが担うもの

- Agent 出力に対する声・文体・表情の付与
- 対話の「間」を埋めるメタ発話（相槌・つなぎ・進捗報告）
- 人格パラメータの保持と、そこからのプロンプト／音声／表情の導出
- 複数人格の管理・編集（管理者向け）
- 人格インスタンスのルームへの入退室と、複数インスタンスの同時稼働（§11）
- 人格の他 Agent への移植
- 人格の交配（Breed）による新人格の生成
- 人間との関係履歴（選好・関係史）の記憶

### 1.3 このレイヤーが担わないもの（重要）

- **タスクに関する判断・推論・回答内容の生成** — すべて Agent 側の責務
- **Agent の回答の書き直し** — §2.1 参照
- 会議UI そのもの（WebRTC、画面共有、音声入出力）— 別コンポーネント
- タスク知識のメモリ — Agent 側のメモリに置く

## 2. 設計原則（不可侵）

実装中に迷ったら、この5項目に戻ること。いずれも守らないと具体的なバグとして表面化する。

### 2.1 人格レイヤーはタスク回答の内容を変えない

Agent が生成したタスク回答は**素通し**する。人格レイヤーが書き直すと、

- LLM 呼び出しが2回になり、リアルタイム音声の遅延要件を満たせない
- キャラクターが業務内容を歪める（キャラが数値を「盛る」等）

人格が乗るのは、回答の**前後**（メタ発話）と、**声・表情**のみ。

> 例外規定：どうしても文体を寄せたい場合は、Agent 側のシステムプロンプトに人格記述を注入する方式のみ許可する。事後書き直しは禁止。

### 2.2 表情と声は LLM に選ばせない

表情・音声パラメータは実行時状態（§6）からの**決定的なマッピング**で決める。LLM に選ばせると遅延が乗り、かつ Agent の応答が返るまで表情が決まらない。「処理中の thinking 表情」が出せなくなり、キャラを置く最大の実利を失う。

### 2.3 メタ発話は原則 LLM を呼ばない

人格ごとに**起動時にテンプレート集をプリベイク**しておき、実行時はテンプレートから選ぶだけにする。これによりメタ発話のレイテンシは実質ゼロになる。

### 2.4 人格の差し替えでコードは変わらない

すべての人格差分は設定データ（§4）に閉じる。分岐を書きたくなったら、それはパラメータ化の失敗。

### 2.5 ランダム性は生成時のみ。実行時は決定的

**Breed（§12）のランダム性は、人格の生成時に1回だけ効く。生まれた人格は決定的に振る舞う。**

実行時にランダム性を入れてはならない。ランダム性は人間らしさを生まない。同じ状況で違う反応をする相手は「人間らしい」ではなく「一貫性がない」であり、不気味さとして知覚される。受け入れ基準2（同一性の一貫性）に直接違反する。

Breed の価値は、設計者が思いつかなかったパラメータの組み合わせに出会えるという**探索**にある。人間らしさの源泉ではない。

> **例外は発話タイミングだけ**：§11.6 の発話権調停で使う微小ジッタ（backoff の衝突回避）は、発話の**内容**を一切変えず、**いつ**喋るかしか動かさないため、この原則に反しない。受け入れ基準10（実行時の決定性）は出力内容についての基準であり、保たれる。

### 2.6 人格インスタンスが単位。中央状態を持たない

**1つの人格 = 1つの独立したインスタンス。** インスタンスは自分の `PersonaState`・`AgentBridge`・`MetaSpeech`・声・表情だけを持ち、他の人格を知らない。

システムは「現在の人格」というグローバル状態を**持たない**。人格が1体だけ動いている状態は、「インスタンスが1つだけルームにいる」として表現する。切り替えは「1体が退室し、別の1体が入室する」であり、特別な操作ではない。

この原則により、1体運用（§11 の基本）と複数体の同時稼働（§11.6 のAI議論）が**同じ仕組み**になる。1体は N=1 の特殊ケースにすぎない。中央オーケストレーターは存在しない。

## 3. システム構成

### 3.0 ルーム + インスタンスモデル

人格レイヤーは、**Room（部屋）** と、そこに入退室する **PersonaInstance（人格インスタンス）** で構成する。中央の制御者はいない。

```
                          ┌─────────── Room ───────────┐
                          │   RoomBus（イベントバス）  │
                          │  - 全発話を配信            │
                          │  - 話者IDを必ず付与        │
                          │  - 全発話・全 bid を記録   │
                          └──┬──────────┬──────────┬───┘
                             │          │          │
              ┌──────────────┴──┐  ┌────┴────┐  ┌──┴──────────────┐
   [人間]────▶│ PersonaInstance │  │ 人間参加│  │ PersonaInstance │
   （参加者） │   〇〇さん      │  │ 者      │  │   △△さん       │
              │ ・PersonaState  │  └─────────┘  │ ・PersonaState  │
              │ ・AgentBridge ──┼──▶ Agent A     │ ・AgentBridge ──┼──▶ Agent B
              │ ・MetaSpeech    │               │ ・MetaSpeech    │
              │ ・声/表情       │               │ ・声/表情       │
              └─────────────────┘               └─────────────────┘

   各 PersonaInstance の内部（1発話の流れ）:
     RoomBus購読 → 発話権判定(§11.6) → filler(即時) → AgentBridge転送
       → タスク回答受信 → 素通し+声・表情 → RoomBusへ発話(話者ID付き)
```

- **人間も1参加者**。人間が1人でもいれば、その人間が議論の司会（議題・打ち切り）を担える（§11.6）
- **各 PersonaInstance は Agent と厳密に 1:1**（§11.1）
- Room は発話を**配信・記録**するが、**誰が喋るかを決めない**（調停は各インスタンスがローカルに行う・§11.6）

### 3.1 コンポーネント

| コンポーネント | 単位 | 責務 |
|---|---|---|
| `PersonaRegistry` | グローバル | 人格定義の CRUD・検証・プリベイク・バージョン管理 |
| `PersonaBreeder` | グローバル | 人格の交配（§12） |
| `PersonaPorter` | グローバル | 人格パッケージのエクスポート／インポート（§10） |
| `Room` | ルーム | 参加者の入退室管理、`RoomBus` の保持 |
| `RoomBus` | ルーム | 発話イベントの配信・記録（話者ID必須・§11.4） |
| `PersonaInstance` | **インスタンス** | 1体の人格の実行時実体。以下を内包する |
| ` ├ PersonaState` | インスタンス | 実行時状態（§4.4） |
| ` ├ AgentBridge` | インスタンス | 接続先 Agent への転送と受信（素通し保証・1:1） |
| ` ├ MetaSpeech` | インスタンス | メタ発話のトリガー判定とテンプレート選択 |
| ` ├ SpeechArbiter` | インスタンス | 発話権のローカル判定（§11.6） |
| ` ├ ExpressionMachine` | インスタンス | 状態 → 表情ID の決定的マッピング（テーブル駆動） |
| ` └ (composer 参照)` | — | `PromptComposer`・`ProsodyComposer` を呼ぶ（純関数・共有可） |
| `PromptComposer` | 純関数 | 人格定義 + 状態 → システムプロンプト文字列 |
| `ProsodyComposer` | 純関数 | 人格定義 + 状態 → SSML prosody 属性（§5.3） |
| `PersonaMemory` | インスタンス | 選好・関係史の書き込みと読み出し |

> **`PersonaRouter` は廃止した（v0.3 まで存在）。** 「切り替え」はルームへの入退室に一般化されたため、専用コンポーネントが不要になった。切り替えロジックは `Room` の入退室に吸収される（§11.3）。

## 4. データモデル

### 4.1 3分割の原則

移植性（§10）とBreed（§12）を成立させるため、従来の PersonaDefinition を**3つに分割する**。

| 単位 | キー | 移植 | 継承（Breed） |
|---|---|---|---|
| `Persona` | personaId | **する** | **する** |
| `PersonaBinding` | personaId × agentId | しない | しない |
| `PersonaMemory` | personaId × userId | しない | しない |

**「得意分野」は Persona ではなく Binding に属する。** キャラクター（呼称・口調・6軸）は不変で、何に詳しいかは接続先の Agent が決める。これにより「投資の〇〇さん」を開発 Agent に繋ぎ直しても、人格はそのままで得意分野だけが入れ替わる。

### 4.2 Persona（移植・継承の単位）

```typescript
interface Persona {
  schemaVersion: '1.0';     // 移植時の互換性判定に使う（§10.3）
  id: string;
  displayName: string;

  // 層1: 同一性アンカー
  anchor: {
    firstPerson: string;        // "私" | "僕" | "俺" | "わたくし" | "あたし" 等
    secondPerson: string;       // "あなた" | "君" | "{name}さん" 等
    verbalTics: string[];       // 語尾・口癖 2〜3個
    refusalLines: string[];     // 言わないこと（最大10件・§12.4）
    freeNote?: string;          // その他の特性（フリーテキスト・任意）
  };

  // 層2: 表出スタイル（各 0〜4 の整数）
  style: {
    distance:    0|1|2|3|4;  // 距離感
    density:     0|1|2|3|4;  // 情報密度
    assertion:   0|1|2|3|4;  // 断定度
    initiative:  0|1|2|3|4;  // 主導性
    affect:      0|1|2|3|4;  // 情動表出（テキストと音声の両方を駆動・§5.3）
    playfulness: 0|1|2|3|4;  // 遊び
  };

  assets: {
    spriteSet: string;    // 表情スプライトの参照（パッケージ内相対パス）
    voiceId: string;      // TTS の声ID
  };

  lineage?: {             // Breed で生成された場合のみ
    parents: [string, string];   // 親→子の一方向。これを辿れば家系図が引ける
    generation: number;          // 親の generation + 1。非正規化キャッシュであり制約ではない
    seed: number;
  };
}
```

**`gender` と `age` フィールドは意図的に存在しない。** §17 参照。
**`expertise` もここには無い。** §4.3 へ移動した。

### 4.3 PersonaBinding（Agent への接続）

```typescript
interface PersonaBinding {
  personaId: string;
  agentId: string;
  expertise: string[];          // この Agent に繋がっている間の得意分野
  outOfScopeStance: string;     // 専門外を聞かれたときの態度（1文）
  invocationAliases: string[];  // 「〇〇さん」で呼び出すときの名前（§11.2）
}
```

### 4.4 PersonaState（実行時・人格ごと・セッションごと）

```typescript
interface PersonaState {
  personaId: string;
  arousal: number;         // 0.0〜1.0  賦活レベル
  familiarity: number;     // 0.0〜1.0  親密度（永続・§6.2）
  lastContactAt: number;   // familiarity の遅延減衰計算に使う
  context: 'idle' | 'listening' | 'thinking' | 'speaking' | 'reporting';
  lastEvent?: 'success' | 'error' | 'correction';
  lastEventAt?: number;
}
```

**人格ごとに独立して保持する。** 〇〇さんへの親密度と △△さんへの親密度は別。

### 4.5 MemoryRecord

```typescript
interface MemoryRecord {
  id: string;
  personaId: string;
  userId: string;
  type: 'preference' | 'correction' | 'episode';
  content: string;       // 1行1事実
  createdAt: number;
  weight: number;        // 0.0〜1.0
}
```

## 5. 層2：表出スタイルの実装

### 5.1 軸の定義と、値→プロンプト文言のマッピング

`PromptComposer` はこの表を引いて、6行の指示文を生成する。**この表が本仕様の中核成果物**であり、チューニングはここだけを触る。

#### distance（距離感）

| 値 | プロンプト文言 |
|---|---|
| 0 | 敬語・丁寧語を徹底する。「〜でございます」「〜いたします」を使う |
| 1 | 標準的な敬体で話す。「〜です」「〜ます」 |
| 2 | 敬体を基本にしつつ柔らかく。「〜ですね」「〜ですよ」 |
| 3 | 常体を混ぜる。「〜だね」「〜かな」 |
| 4 | 常体で話す。「〜だよ」「〜じゃん」 |

#### density（情報密度）

| 値 | プロンプト文言 |
|---|---|
| 0 | 結論のみを一文で述べる。補足しない |
| 1 | 結論と、一言の理由を述べる |
| 2 | 結論・理由・必要な前提を述べる |
| 3 | 結論・理由・前提に加え、関連する周辺情報を添える |
| 4 | 背景・経緯・代替案まで説明する |

#### assertion（断定度）

| 値 | プロンプト文言 |
|---|---|
| 0 | 常に留保をつける。「〜かもしれません」「断定はできませんが」 |
| 1 | 確度を明示する。「おそらく」「たぶん」 |
| 2 | 確かなことは言い切り、不確かなことにのみ留保をつける |
| 3 | 基本的に言い切る。留保は重要な場合のみ |
| 4 | 常に言い切る。「〜です」「〜すべきです」 |

#### initiative（主導性）

| 値 | プロンプト文言 |
|---|---|
| 0 | 聞かれたことにのみ答える。提案しない |
| 1 | 求められれば補足する |
| 2 | 関連して有用なことがあれば一言添える |
| 3 | 次にやるべきことを提案する |
| 4 | 先回りして選択肢を提示し、推奨を述べる |

#### affect（情動表出）

| 値 | プロンプト文言 |
|---|---|
| 0 | 感情語を使わない。平板に述べる |
| 1 | 最小限の相槌のみ |
| 2 | 状況に応じて反応する。「なるほど」「それは大変ですね」 |
| 3 | 感情を明示する。「嬉しいです」「困りましたね」 |
| 4 | 抑揚豊かに。感嘆・驚き・喜びを表に出す |

> **インターフェース用途では 1〜2 を推奨、上限を 2 に制限することを検討すること。** 3以上は業務対話では過剰に感じられやすい。

#### playfulness（遊び）

| 値 | プロンプト文言 |
|---|---|
| 0 | 脱線や冗談を一切入れない |
| 1 | ごく稀に軽い一言を添える |
| 2 | 場面に応じて軽口を混ぜる |
| 3 | 冗談や比喩を頻繁に使う |
| 4 | 常に遊びを混ぜる |

### 5.2 なぜ 5段階なのか（変更しないこと）

- 10段階は人間も LLM も区別できない。7 と 8 の差は出力に現れない
- 6軸 × 5段階 = 15,625通り。用途に対して十分
- 各軸が**出力の観測可能な特徴**に対応しているため、評価（§15）と自動チューニングが可能
- **移植（§10）と交配（§12）が、整数6個の受け渡しで済む**

### 5.3 音声の抑揚（`affect` 軸が両方を駆動する）

テキストと音声で情動表出がズレる問題は、**駆動源を1つにすることで原理的に解消する**。ズレは「テキストは平板なのに声が陽気」という状態から起きるので、`affect` 軸がテキスト（§5.1）と音声（本節）の両方を決めているなら、発生しない。

実装は **SSML の `prosody` 属性のみ**。感情タグ対応 TTS は使わない（コスト増・ベンダーロックイン・§15 の非機能要件を満たせない）。

`ProsodyComposer` は次の静的テーブルを引くだけ。**追加コスト・追加レイテンシはゼロ。**

| `affect` | rate | pitch |
|---|---|---|
| 0 | 95% | -1st |
| 1 | 100% | +0st |
| 2 | 105% | +1st |
| 3 | 110% | +2st |
| 4 | 115% | +3st |

`arousal`（§6.1）による補正:

```
rate_final = rate_base + round(arousal * 5)   // 単位: %
```

出力例:

```xml
<prosody rate="107%" pitch="+1st">できました、共有しますね</prosody>
```

## 6. 層3：状態エンジン

### 6.1 arousal（賦活レベル）

```
減衰:   arousal(t) = arousal_0 * exp(-Δt / τ)      τ = 180 秒
加算:   ユーザー発話受信      +0.15
        タスク成功            +0.25
        ユーザーによる訂正    +0.10
        エラー                +0.20
クリップ: [0.0, 1.0]
```

**効果**：メタ発話の頻度と長さ、および音声の rate（§5.3）。

```
メタ発話長さ係数 = 0.7 + 0.6 * arousal
```

### 6.2 familiarity（親密度）

**上昇速度 > 減衰速度** となるよう設計する。減衰にバッチジョブは使わない。**読み出し時の遅延計算**のみ。

```
上昇:  セッション終了時に  familiarity += 0.03   （クリップ上限 1.0）

減衰:  読み出し時に、最終接触からの経過日数 d を用いて
       familiarity_effective = familiarity_stored * (0.99 ** d)
       ※ 読み出したら familiarity_stored も更新し、lastContactAt を現在時刻にする
```

均衡点（設計意図の確認用）:

| 利用頻度 | familiarity の収束先 |
|---|---|
| 毎日 | 1.0（上限に張り付く） |
| 週1 | 約 0.43 |
| 月1 | 約 0.12（ほぼ初対面に戻る） |

**効果**：`distance` 軸へのオフセット。

```
effective_distance = clamp(style.distance + round(familiarity_effective * 1.5), 0, 4)
```

これで「初対面は丁寧、慣れると砕ける、久しぶりだとまた少し他人行儀」が、追加パラメータなしで出る。

### 6.3 context（会話文脈）

| 状態 | 遷移条件 |
|---|---|
| `idle` | 直近3秒に入出力なし |
| `listening` | ユーザーの入力/発話を受信中 |
| `thinking` | Agent へ転送済み、応答待ち |
| `speaking` | 応答を音声出力中 |
| `reporting` | 画面共有・資料提示中 |

**すべて Agent の応答を待たずに確定できる。** これが §2.2 の前提。

## 7. メタ発話

### 7.1 トリガーと種別

| トリガー | 種別 | 例 |
|---|---|---|
| ユーザー発話の受領 | `backchannel` | 「はい」「なるほど」 |
| Agent 呼び出し開始 | `filler` | 「ちょっと調べますね」 |
| 処理が 3秒 を超過 | `progress` | 「もう少しかかりそうです」 |
| Agent 応答の受信直前 | `handoff` | 「できました、共有します」 |
| エラー発生 | `apology` | 「すみません、失敗しました」 |
| 人格の切り替え | `handover` | 「〇〇さんに代わりますね」（§11.3） |

### 7.2 プリベイク

起動時（および人格の編集・生成時）、人格ごとに各種別 × 5〜8 バリエーションを生成し、キャッシュする。生成は LLM で行ってよい（1回のみ）。

```
入力: Persona の anchor + style
出力: { backchannel: string[], filler: string[], progress: string[],
        handoff: string[], apology: string[], handover: string[] }
```

実行時は**このキャッシュから選ぶだけ**。LLM を呼ばない。連続で同じものを選ばないこと（直近2件を除外）。

> 選択自体は擬似ランダムだが、これは §2.5 に反しない。テンプレート集そのものが人格の関数として決定的に生成されており、どれを引いても人格の同一性は保たれるため。

### 7.3 タイミングと長さ制限

`filler` は Agent への転送と**同時**に発話を開始する。Agent の応答を待たない。これによりユーザーの体感待ち時間が消える。

**`filler` と `backchannel` は、読み上げ 1.5秒以内に収まる長さに制限すること。**

これは「ユーザーが話し始めたときに filler を中断するか」という問題への解でもある。長さで抑えれば、言い切っても邪魔にならないため、割り込み判定の実装が不要になる。v1 では割り込みを実装しない。

> ただし将来の割り込み対応のため、TTS ラッパーは `stop()` を持つインターフェースにしておくこと。

## 8. 表情ステートマシン

### 8.1 マッピング（テーブル駆動）

**このマッピングはコードの `switch` 文で書かず、必ず設定テーブルとして持つこと。** 表情の追加が「アセット＋テーブル1行」で済むようにするため。

```
基本:      context → 表情ID
  idle       → neutral
  listening  → listening
  thinking   → thinking
  speaking   → speaking
  reporting  → speaking        ← v1 は流用。実機を見て必要なら独立表情を追加

一時上書き（lastEvent 発生から 2.0 秒間）:
  success    → pleased
  error      → puzzled
  correction → puzzled
```

### 8.2 アセット仕様

- 表情ID：`neutral` / `listening` / `thinking` / `speaking` / `puzzled` / `pleased` の6種
- 各表情 3コマのループ、3fps（333ms/フレーム）
- **1体あたり 18枚**の静止画で全表情を賄える
- 形式：WebP（透過）、推奨 512×512
- `speaking` のみ口の開閉2コマ + 閉じ1コマの構成にすること

### 8.3 遷移

- 遷移時間 50ms 以内
- クロスフェードなし（3fps のパラパラ感を保つ）

## 9. メモリー

### 9.1 書き込みトリガー（機械的に固定）

「重要・強烈な事項」を LLM に毎回判定させない。以下の4条件のいずれかに合致した場合のみ書き込む。判定は軽量な分類器1回で行う。

| 条件 | type | weight |
|---|---|---|
| ユーザーが明示的に依頼（「覚えておいて」） | `preference` | 1.0 |
| ユーザーが Agent の誤りを訂正した | `correction` | 0.8 |
| 選好の表明（「〜は嫌い」「〜の方がいい」） | `preference` | 0.6 |
| タスクの完了 / 失敗 | `episode` | 0.4 |

「強烈さ」という主観量の推定より、桁違いに安定する。

### 9.2 読み出し（責務分離）

**人格レイヤーが読むのは `preference` と `episode` のみ。** タスク知識は Agent 側のメモリに置き、人格レイヤーは触らない。混ぜると、キャラクターが業務知識を歪めるバグになる。

読み出し量：直近 10件 + weight 上位 5件を、システムプロンプトに注入。

### 9.3 メモリーは移植・継承されない

- **移植（§10）**：エクスポートされたパッケージにメモリーは含まれない
- **交配（§12）**：子はメモリーを継承しない。`familiarity` も 0 から

## 10. 人格の移植

### 10.1 パッケージ形式

```
<persona-id>.persona/          ← zip 可
  manifest.json                ← Persona（§4.2）そのもの
  sprites/
    neutral_0.webp … pleased_2.webp    （18枚）
  voice.json                   ← TTS 設定（voiceId とベンダー非依存の記述）
```

**メモリー・Binding は含まれない。**

### 10.2 移植手順

1. `PersonaPorter.export(personaId)` → `.persona` パッケージ
2. 移送
3. `PersonaPorter.import(package)` → `schemaVersion` を検証し、`Persona` を登録
4. 管理者が新しい `PersonaBinding`（§4.3）を作成し、得意分野を設定
5. `MetaSpeech` のプリベイク（§7.2）を実行

インポート直後の人格は、**口調・声・表情は完全に同一で、得意分野とメモリーだけが空**の状態になる。

### 10.3 互換性の契約

- `§5.1 の文言マッピング表` と `§5.3 の prosody テーブル`は、**パッケージに含めない**。受け入れ側のランタイムが持つ
- したがって受け入れ側は、同じ6軸・同じ5段階を実装している必要がある
- この整合は `schemaVersion` で判定する。不一致はインポート時に拒否
- `voiceId` は移植先の TTS ベンダーが異なると解決できない。`voice.json` には**ベンダー非依存の記述**（性別傾向・話速基準・音域）を併記し、移植先が最も近い声にフォールバックする

### 10.4 なぜこれが成立するか

人格の実体が「整数6個 + 文字列数個 = 約1KB の JSON」に落ちているため。**120次元の元型ベクトルのままだったら、移植先が同じ解釈をする保証がなく、この要件は満たせなかった。**

## 11. ルーム・入退室・発話権

人格の実行時モデルは、Room に PersonaInstance が入退室する形（§3.0）。「1体だけ」も「複数体で議論」も、この1つの仕組みで表現する。

### 11.1 管理と 1:1 制約

- `PersonaRegistry` が人格定義の CRUD を提供。管理者UIから全パラメータを編集可能
- **編集は新バージョンを作る。稼働中のインスタンスは旧バージョンを保持する。** 会話の途中で人格が変わるのを防ぐため
- 編集後は `MetaSpeech` のプリベイクを再実行する
- 権限は**「人格管理者」ロール1つ**。人格の編集と Breed（§12）を分離しない
- **1 PersonaInstance = 1 Agent（厳密に 1:1）。**
  - 人格定義（`Persona`）は複数の Agent に Binding できる（§4.3）が、**実行時にインスタンス化されたら、その1体は1つの Agent にだけ繋がる**
  - 同じ人格を別々の Agent で使いたいなら、別々のインスタンスとして起動する（それぞれ別の Binding を選ぶ）
- **同一人格の同一 Agent へのインスタンスは、1ルームにつき1つまで。** これを許すと「同じ人が同じ部屋に二重に入る」状態になる。入室時に (personaId, agentId) の重複を弾く

### 11.2 入室（「〇〇さんを出して」）

**トピックによる自動ルーティングは実装しない。** 誤ルーティングは強い違和感を生み、複雑さに見合わない。入室はすべて明示。

- **明示入室のみ**：「〇〇さんを出して」「〇〇さんに聞きたい」→ `PersonaBinding.invocationAliases` を照合し、該当人格のインスタンスをルームに入室させる
- **提案は許可**：ルーム内のある人格が、自分の `expertise` 外の質問を受けたとき、`outOfScopeStance` に沿って別人格を提案してよい

  > 「それでしたら投資に詳しい〇〇さんがいいと思います。呼びますか？」

  提案の判定は Binding の `expertise` 照合のみ。追加の LLM 呼び出しは不要
- 入室した人格は `handover`／`backchannel` で自己開示してよい（「〇〇です、よろしく」）

### 11.3 退室と「切り替え」

**「人格の切り替え」は、独立した操作ではない。** 「A が退室し B が入室する」の組み合わせにすぎない。

- 1体だけにしたい運用（§11 の基本）では、新しい人格を入室させる前に、今の人格を退室させる。結果として常にルーム内は1体
- 複数体を残したい運用（§11.6）では、退室させずに追加入室させる
- どちらも `Room.enter(persona, agent)` / `Room.leave(instanceId)` の2操作だけで表現される。**専用の「切り替え」コードは書かない**

会話履歴（タスク文脈）は各 Agent 側が保持しているため、入退室で失われない。

### 11.4 RoomBus（イベントバスであって、調停者ではない）

ルーム内の共有文脈は `RoomBus` が持つ。各 PersonaInstance と各人間参加者は、これを購読する。

- **配信するイベント**：発話開始、発話内容（確定テキスト）、発話終了、入室、退室
- **`speakerId` は全イベント必須。** これが無いと、AIが自分自身の発言に反応して無限ループに陥る。実装上の最重要フィールド
- **RoomBus は「誰が喋るか」を決めない。** 配信するだけ。調停は各インスタンスがローカルに行う（§11.6）
- **RoomBus は全発話・全 bid（§11.6）を時刻付きで記録する。** 調停はしないが記録はする。分散モデルのデバッグはこのログが命綱（§11.7）

### 11.5 コンテキスト注入（誰の発言かを人格に伝える）

各 PersonaInstance が Agent を呼ぶとき、`RoomBus` の直近発話を文脈として渡す。このとき:

- 各発話に**話者名を明示**する（「〇〇さん:」「利用者:」）。これがないと、誰の主張に答えているのか Agent が取り違える
- **自分の過去発話も含める**が、「（自分）」と印をつける。自己参照の混乱を防ぐ
- 人間の発言と他 AI の発言を区別できるようにする

### 11.6 発話権（中央調停なしの分散プロトコル）

複数体が同時にルームにいるとき、誰が喋るかを**各インスタンスがローカルに決める**。中央の司会コンポーネントは持たない。方式は CSMA/CD（Ethernet の衝突検出）と同型。

各 `SpeechArbiter` のループ:

```
1. carrier sense : RoomBus に「発話中」イベントがあるか聞く
2. 発話中なら待つ。空いたら 3 へ
3. 自分が喋るべきか判定（下記の bid 条件）
4. 喋るべきなら backoff 時間だけ待つ
5. backoff 満了時にまだ空いていれば発話開始（RoomBus に bid→発話を記録）
   誰かが先に始めていたら諦めて 1 へ戻る
```

**backoff を `initiative` 軸の関数にする。** これにより発話権が人格から自然に出る（主導性の高い人格ほど先に喋る）。追加パラメータは不要。

| `initiative` | backoff 基準値 |
|---|---|
| 4（先回りして提案） | 200ms |
| 3 | 400ms |
| 2 | 600ms |
| 1 | 900ms |
| 0（聞かれたら答える） | 1200ms |

```
backoff = base(initiative) + jitter(0〜120ms)   // jitter は衝突を割るためだけ・§2.5 例外
```

**bid 条件**（喋るべきかの判定・LLM を呼ばない軽量判定）:
- 直前の発話が自分宛て（名前を呼ばれた、質問された）→ 高優先で bid
- 直前の発話が自分の `expertise` に関係する → 通常 bid
- 直前が自分の発言 → **連続発話を避けるため bid しない**（一方的な独演を防ぐ）
- 直近 N ターン自分が一度も喋っていない → bid 優先度を上げる（沈黙しっぱなしを防ぐ）

> **重要（§2.1 の再確認）**：議論の**内容**は各 Agent が生成する。人格レイヤーは「いつ・誰が喋るか」（タイミング）と「どう聞こえるか」（声・表情）だけを担う。AI議論の知的な中身は Agent 側にあり、人格レイヤーの範囲外。

### 11.7 終了条件（分散では解けない唯一の残余）

発話権は分散で解けるが、**「議論を終える」判定は分散では解けない。** ローカルには「議論が尽きた」を知る手段がないため、放置すると AI同士が同意し続けるか発散する。

議題・時間・打ち切りを**誰かが所有する**必要がある。ただしこれは**システム階層ではなく、参加者の役割**として置く:

- **人間が1人でもルームにいる場合**：その人間が司会。追加コンポーネントは不要。**「Meet に人間1＋AI複数」というご想定のユースケースは、これに該当し、終了条件の実装が要らない**
- **AIだけの無人議論をさせる場合のみ**：「議題と時間を持つ人格」を1体、司会として入室させる。これも通常の PersonaInstance であり、専用階層ではない。司会人格は打ち切り発話（`progress`/`handover` テンプレートの延長）を持つ

安全弁として、**ルームに発話ターン数の上限**を設け、超過したら強制的に司会（人間 or 司会人格）へ制御を戻す。無限ループの最終防波堤。

### 11.8 v1 のスコープ

- **v1 で実装する**：Room / RoomBus / PersonaInstance / 入退室 / §11.6 の発話権プロトコル / 人間司会
- **v1 で実装しない（後付け可）**：AIだけの無人議論のための「司会人格」。仕組み上は通常の人格1体なので、人格を1つ用意すれば足りる。急がないなら後回しでよい

## 12. Breed 機能

人格を2体まで組み合わせ、新しい人格を生成する。**§2.5 の通り、ランダム性は生成時に1回だけ効く。**

### 12.1 インターフェース

```typescript
interface BreedRequest {
  parentA: string;
  parentB: string;
  seed?: number;           // 省略時は自動生成。必ず結果に記録する
  mutationRate?: number;   // 既定 0.15
}
```

**`seed` は必ず `Persona.lineage` に保存すること。** 同じ親 × 同じ seed が同じ子を生むこと（再現性）は、デバッグと「もう一回」の両方に必須。

### 12.2 style の交配（一様交叉 + 突然変異）

```
for each axis in [distance, density, assertion, initiative, affect, playfulness]:
    v = rand() < 0.5 ? A.style[axis] : B.style[axis]     // 一様交叉
    if rand() < mutationRate:
        v += rand() < 0.5 ? -1 : +1                       // 突然変異
    child.style[axis] = clamp(v, 0, 4)
```

**単純平均を使ってはならない。** 平均を取ると子が中央値に収束し、何度交配しても同じような人格しか出てこない（分散が世代ごとに半減する）。一様交叉なら、各軸の値は親のどちらかそのものなので、母集団の分布が保たれる。

### 12.3 anchor の交配

`anchor` は文字列であり数値的にブレンドできないため、要素ごとに演算が異なる。

| 要素 | 演算 | 理由 |
|---|---|---|
| `firstPerson` / `secondPerson` | **セットで片親から丸ごと継承** | バラすと「わたくし」×「お前」のような破綻した組み合わせが生まれる |
| `verbalTics` | 各親から 1〜2個をサンプリングし、計2〜3個に | 混成が最も耳に出る箇所。ここが Breed の面白さの本体 |
| `refusalLines` | **和集合**（重複除去・§12.6） | 交叉させると、片親が禁じていたことを子が言い出す |
| `freeNote` | 片親から丸ごと | |

### 12.4 継承しないもの

| 項目 | 扱い |
|---|---|
| メモリー | 継承しない。空で生まれる |
| `familiarity` | 継承しない。0 から |
| Binding（得意分野） | 継承しない。**子は未接続で生まれ、管理者が Binding する** |
| `assets`（画像・声） | 自動生成できない。片親から継承するか、既定アセットで生まれる。管理者が割り当てる |

### 12.5 系譜（親→子の一方向のみ）

- 遺伝は**親→子の一方向**のみ。`lineage.parents` を辿れば家系図が引ける
- 逆引き（ある人格の子を列挙する）のため、`lineage.parents` に対するインデックスを張ること
- **世代数の上限は強制しない。警告も出さない。** §12.6 の通り実用範囲は3世代程度だが、それは仕様書の記述に留め、システムは制限しない

> **落とし穴：親の削除**。人格を物理削除すると `lineage.parents` の参照が切れ、家系図が壊れる。**人格の削除は論理削除（tombstone）とし、レコード自体は残すこと。** 削除済みの親は家系図上でグレー表示にする。これは §11.1 の CRUD の設計に直接効くため、Phase 6 の時点で決めておくこと。

### 12.6 既知の制約（仕様として受け入れる）

- **`refusalLines` の累積**：和集合なので世代を重ねると増え続け、いずれ何も言えない人格になる。**上限10件**とし、超えた場合は生成を止めて管理者に選別を求める。初期人格の `refusalLines` は**2〜3件**に抑えること（粗く書く）。ここを細かく書くと、2世代で上限に当たる
- **世代を重ねると親の面影が消える**：突然変異が各軸をランダムウォークさせるため、5世代以降は初期人格とほぼ無関係な値に拡散する。実用範囲は3世代程度。**これは仕様であり、バグではない**
- **画像の交配はできない**：見た目のブレンドは別スコープ（画像生成の導入が必要）

### 12.7 生成後の検証

- §15 の受け入れ基準2（同一性の一貫性）を自動実行し、通らなければ破棄して再生成（同じ seed からは同じ結果になるので、seed を変える）
- 破綻ではないが極端な組み合わせ（例：`distance=0`「わたくし・でございます」× `playfulness=4`）は**警告のみ。禁止しない**。想定外の組み合わせに出会うことが Breed の目的であるため

### 12.8 副次的な利得

Breed はランダム人格の大量生成器なので、**受け入れ基準3・4（軸の有効性・直交性）のテストデータ生成にそのまま使える**。評価パイプラインから呼べるようにしておくこと。

## 15. 受け入れ基準

| # | 基準 | 測定方法 |
|---|---|---|
| 1 | 素通しの保証 | Agent 出力とユーザー到達テキストの、タスク回答部分が完全一致すること（自動テスト） |
| 2 | 同一性の一貫性 | 同一人格で 20回対話し、一人称・語尾の一貫性が 95% 以上 |
| 3 | 軸の有効性 | `distance` を 0→4 に振った出力を盲検で提示し、人間が順序を当てられること。6軸すべてで実施 |
| 4 | 軸の直交性 | ある軸のみを動かしたとき、他の軸の観測値が有意に動かないこと |
| 5 | メタ発話の先行 | `filler` の発話開始が、Agent 応答の受信より必ず早いこと |
| 6 | 表情の決定性 | 同一の状態列に対し、常に同一の表情列が出ること |
| 7 | 移植の同一性 | export → import した人格が、同一入力に対し移植前と同一の文体・prosody を出すこと |
| 8 | Breed の再現性 | 同一の親 × 同一 seed から、常に同一の子が生成されること |
| 9 | Breed の多様性 | 同一の親から seed を変えて 50体生成し、各軸の分散が親の分散と同等以上であること（平均収束が起きていないことの検出） |
| 10 | 実行時の決定性 | 同一人格・同一状態・同一入力に対し、タスク回答の文体が一定であること（§2.5） |
| 11 | 自己反応の非発生 | ルームに2体を入れ、`speakerId` を根拠に、いずれのインスタンスも自分自身の発話に反応しないこと（§11.4） |
| 12 | 発話権の秩序 | `initiative` の異なる2体をルームに入れ、沈黙後の初手を主導性の高い方が取る頻度が有意に高いこと（§11.6）。かつ、どちらか一方が連続独演しないこと |

**基準3・4が本仕様の生命線。** ここが通らない軸は、軸として機能していないので、文言（§5.1）を修正するか軸自体を差し替える。
**基準9は §12.2 の一様交叉が正しく実装されているかの検出器。** 単純平均を書いてしまうと、ここで必ず落ちる。
**基準11 は AI議論の安全弁。** ここが落ちると無限ループになる。2体運用を有効化する前に必ず通すこと。

## 16. 実装フェーズ

| Phase | 内容 | 完了条件 |
|---|---|---|
| 1 | データモデル（3分割）+ `PromptComposer` + §5.1 の文言表 | 受け入れ基準 3・4 |
| 2 | `AgentBridge`（素通し）+ `StateEngine` | 受け入れ基準 1 |
| 3 | `MetaSpeech`（プリベイク）+ `ProsodyComposer` | 受け入れ基準 5 |
| 4 | `ExpressionMachine` + アセット1体分 | 受け入れ基準 6 |
| 5 | `PersonaMemory` | — |
| 6 | `PersonaRegistry` + 人格編集UI + プリセット | 受け入れ基準 2 |
| 7 | `Room` + `RoomBus` + 単一 `PersonaInstance` の入退室 | 受け入れ基準 10 |
| 8 | `PersonaPorter`（移植） | 受け入れ基準 7 |
| 9 | `PersonaBreeder` | 受け入れ基準 8・9 |
| 10 | 複数 `PersonaInstance` の同時稼働 + `SpeechArbiter`（§11.6）+ 人間司会 | 受け入れ基準 11・12 |

Phase 1 単体で「人格が乗った Agent」として動くこと。以降は積み増し。

**Phase 7 の時点で、1体運用も「N=1 のルーム」として実装すること（§2.6）。** ここで「現在の人格」というグローバル変数を1つでも作ると、Phase 10 が作り直しになる。Phase 10 は「N を 1 から増やし、`SpeechArbiter` を1つ足す」だけで済むはずで、済まないなら Phase 7 の設計が誤っている。

Phase 8・9 は Phase 1 のデータモデル分割（§4.1）が正しければ、ほぼ追加実装なしで乗る。**逆に、Phase 1 で `expertise` を Persona に入れてしまうと Phase 8 で作り直しになる。**

Phase 10 は AI議論を有効化するが、**人間が1人いれば司会は不要（§11.7）**。無人議論用の「司会人格」は Phase 10 に含めず、必要になってから通常の人格として1体用意すればよい。

## 17. やらないこと（明示）

実装者が「良かれと思って」追加しがちなもの。いずれも禁止。

| 項目 | 理由 |
|---|---|
| 12の元型 × 10段階（120次元） | 元型は排他的な型であって連続量ではない。「賢者8・道化8」が定義できない。LLM が従えず、評価もできず、移植先が同じ解釈をする保証もない |
| `gender` / `age` の独立パラメータ | LLM に「25歳女性」と入れると学習データ由来の紋切り型が出て制御が効かない。日本語では一人称・二人称・語尾で性別も年齢も距離感もほぼ決まるため、そちらに吸収する（見た目としての画像は `assets` で別途指定） |
| 派生パラメータとしての「性格」 | 層1 + 層2 がそれ自体。二重管理になる |
| `expertise` を Persona に置く | 移植（§10）が成立しなくなる |
| LLM による表情・prosody の選択 | §2.2 |
| Agent 回答の事後書き直し | §2.1 |
| 実行時のランダム性 | §2.5。人間らしさではなく不気味さになる |
| Breed の単純平均 | §12.2。子が中央値に収束する |
| トピックの自動ルーティング | §11.2。誤ルーティングの違和感が複雑さに見合わない |
| 感情タグ対応 TTS | §5.3。SSML prosody で足りる。コスト増とベンダーロックインに見合わない |
| 「現在の人格」をグローバル状態で持つ | §2.6。1体運用も N=1 のルームで表現する。これを破ると Phase 10 が作り直しになる |
| 中央オーケストレーター／司会コンポーネント | §11.6。発話権は各インスタンスがローカルに決める。終了条件は参加者（人間 or 司会人格）が担う |
| `RoomBus` に調停ロジックを持たせる | §11.4。バスは配信・記録のみ。喋る順を決めた瞬間に中央調停に退化する |
| `speakerId` を省く | §11.4。AIが自分の発言に反応して無限ループになる |
| 実行時の発話タイミング以外へのランダム性 | §2.5。jitter は発話タイミングのみ許可。内容には一切入れない |
| 人格の物理削除 | §12.5。家系図の参照が切れる。論理削除（tombstone）にすること |
| Breed の世代数制限 | §12.5。系譜さえ残っていれば、制限する理由がない |
| 軸の追加（7軸目以降） | 直交性が崩れ、矛盾した設定が量産される。追加したくなったら、既存軸の文言（§5.1）で表現できないか先に検討する |
